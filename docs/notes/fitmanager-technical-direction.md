# FitManager: technical direction

This document is **direction, not mandate**. A more capable AI will do the implementation; where it finds a better approach, it should say so rather than follow this blindly. Everything here can be replaced by something that serves the feature list in [the planning document](/documents/6c31f4e8/) better.

The only hard requirements: **TypeScript end to end, with Astro for the web app**, payments through **Creem.io**, and the domain logic (credits, packs, expiry, consumption, reminders) living in our own code, never inside a third-party calendar or scheduler.

## Architecture shape

- **Astro for the site**: server-rendered pages for profiles, admin views, history, settings.
- **Astro islands for the interactive parts**: the calendar, booking buttons, notification panel. An island is a small client-side component embedded in an otherwise static page. React is the likely island framework purely because calendar libraries support it best; Vue or Solid are fine alternatives if the implementer prefers.
- **Domain layer separate from everything**: booking rules, credit consumption (on event date, automatically, for all booked participants), pack stacking (closest-to-expiry first), cutoff windows and reminder triggers live in a framework-free TypeScript module. Neither Astro, the calendar library nor the payment provider should see or bend these rules. This is the part of the app that is the product; keep it the most tested and the most boring code in the repo.
- **Database**: any hosted Postgres (Supabase or Neon are the obvious choices). Nothing in the feature list needs a special database; pick whichever gives the simplest auth story, since member accounts and admin roles are needed on day one.
- **Reminders, phase 1**: in-app notifications only, generated by the app itself. A scheduled job that runs daily and fires the three reminder types from the settings: almost out of credits, plan almost expiring, inactive member with plan expiring soon. Email is a later phase; the notification table should store the channel so email can be added without reworking the logic.

## Frontend calendar

The one piece worth borrowing instead of building. Direction, not a rule:

- **First choice: Schedule-X** (MIT core, TypeScript, framework-agnostic with React and Vue bindings). Lightest option, modern code, day/week/month grids that work on desktop and mobile. Status: **not yet verified**, the docs site timed out during research; the implementer should confirm licence, mobile behaviour and event-rendering API before committing.
- **Fallback: FullCalendar** (MIT core). Heavier and more config, but extremely mature and works everywhere. Its premium (paid) plugins are not needed here.
- **Not recommended**: building a week-grid calendar from scratch. Weeks of UI work with no product value.
- **What the calendar must not do**: hold availability, booking rules or credit logic. It renders slots and calls our API. The coach view is the same component in edit mode; the member view is read-only with Book actions.
- **Worth considering**: members in fitness booking apps often prefer a simple **day list with cards** over a dense grid. That list is easy to hand-build in Astro, possibly with no island at all, so a hybrid is plausible: borrowed week grid for the coach, hand-built day list for members. Decide after a first prototype, not before.
- **Reference for the look and feel**: Thunderbird Appointment ([github.com/thunderbird/appointment](https://github.com/thunderbird/appointment)) is a self-hosted scheduler with a nice-looking booking UI. Its backend is Python and it is a whole product, so it is not reusable as an engine here; browse it for interaction design only. Its slot model may also answer design questions such as whether a group slot carries capacity; its docs are thin, so read the code if needed.

## Payments (Creem.io)

- Checkout for the three pack types: single class, trimester 10-pack, expiring 10-pack (14 weeks).
- Webhooks for successful payments, granting credits automatically. Webhook handling is needed **even if** payment records live in Creem.io's API rather than our database (still an open question in the planning document).
- The manual credit-grant tool in the back office must exist regardless, for goodwill and corrections, and every manual change should be logged.

## Reference repos (read for ideas, do not port code)

- **StudyAppt** ([github.com/zxwangbingbing/StudyAppt](https://github.com/zxwangbingbing/StudyAppt)): class-hour booking with credits, rosters, deduction records, admin credit adjustments. It is a WeChat mini-program, so the code is not reusable; the value is its domain model. An afternoon reading how it models slots, deduction records and back-office adjustments will save schema mistakes.
- **FitMart** ([github.com/parthbuilds-community/FitMart](https://github.com/parthbuilds-community/FitMart)): MIT, MERN fitness platform with admin dashboard, Razorpay payments, transactional email. Reference for admin dashboard structure and a payments webhook flow; stack does not match ours, so again ideas only.

## Design principles

Clean code, SOLID, DRY, KISS, as in the planning document. The one practical translation that matters: **the domain rules should be plain TypeScript functions with tests, independent of Astro, the database client and any UI library**. If swapping Astro for anything else would not break the booking rules, the architecture is right.

## Open before implementation

1. Verify Schedule-X: licence, mobile behaviour, event rendering, island compatibility.
2. Pick the island framework (React by default, not enforced).
3. Decide payment records: our database or Creem.io API as record of truth.
4. Decide whether a no-show flag is needed on attendance for history and gamification.
